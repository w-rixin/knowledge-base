### 核心结论

Rust 代码层改造量 ≈ 0。项目已为跨平台而写，关键依据：
- `Cargo.toml:119` 桌面依赖已用 `cfg(any(windows, macos, linux))` 分组

- `lib.rs:930` 已写好 `#[cfg(target_os="linux")] libpdfium.so` 路径
- `ocr.rs:58` 已写好 `#[cfg(unix)]` 自动 chmod +x
- `converter.rs:160` 非 Windows 走 `soffice`
- `capabilities/default.json` 的 platforms 已含 linux
- `resources` glob `resources/ocr/RapidOCR-json*` 已能同时匹配 .exe 与无扩展名 Linux 版

### 真正障碍（3 个）

1. **webkit2gtk-4.1 缺失**（环境层最硬）：Tauri 2 硬依赖 4.1，麒麟 V10 SP1/SP2 源里只有 4.0。

2. **RapidOCR-json.exe**（16MB Windows PE）：需 Linux aarch64 版，官方 Release 多为 x64，可能需自行 PyInstaller。
3. **pdfium.dll**（7MB Windows DLL）：PDFium 无官方 Linux 预编译，需从源码（gn/ninja）编译。

**重要：后两者缺失时均优雅降级**，不阻断启动：
- pdfium 缺失 → `lib.rs:939` 仅 log::warn，PDF 退回 pdf-extract 主路径
- OCR 缺失 → `ocr.rs:214` is_available() 检查文件存在性，功能自动关闭
→ 策略：可先出「无 OCR 的可用版本」，降低首版风险。

### 关键技术决策：为何用平台专属配置文件而非 targets 数组

tauri-bundler 对 deb/rpm/dmg 有 cfg 门控（跨平台自动跳过），但 **nsis 被刻意不 cfg 门控**
（为支持 Linux/mac 上用 cargo-xwin 交叉打 Windows 包）。
若把 `["nsis","deb"]` 写在同一数组，在麒麟上执行 tauri build 会尝试交叉构建 Windows 安装包。
故采用 tauri.linux.conf.json 覆盖，合并语义为 RFC 7386 JSON Merge Patch（对象递归合并、数组整体替换）。
注意 `linux.deb.depends` 是**追加**而非替换 tauri-bundler 自动计算的依赖。

### 遗留风险

1. webkit2gtk-4.1 无官方麒麟源，属外部依赖，需与 IT 部门确认可获得性
2. OCR 引擎 aarch64 包未必现成
3. PDFium 需源码编译，C++ 工具链有成本
4. 麒麟 kysec 安全模块可能拦截 .deb 内 sidecar 启动，需 IT 放行
5. fonts-noto-cjk 包名在部分麒麟版本不同
6. 建议优先麒麟 aarch64 原生构建，不从 Windows 交叉编译（glibc + webkit 链接会反复阻塞）

### 🔴 重要技术发现：Tauri updater 在 Linux 上不支持 deb

官方行为：`createUpdaterArtifacts` 在 Linux 上只从 **AppImage** 生成
`.AppImage.tar.gz` + `.sig`（v1Compatible 模式），**deb 不生成 updater 产物**。
故麒麟装 deb 后应用内「检查更新」不会有提示 —— 框架限制，非配置错误。

应对：麒麟场景建议 deb + 人工升级（`apt install ./新版本.deb` 自动替换同包）。
改 AppImage 可启用自动更新，但 **kysec 会拦 FUSE 挂载**（需 `kysecctl --disable`
或 `APPIMAGE_EXTRACT_AND_RUN=1`），且麒麟生态以 deb 为主，得不偿失。

注：`plugins.updater` 配置与 pubkey 三平台共用，无需改动；Win/macOS 自动更新不受影响。

### 离线场景的两个固有限制

1. 自动更新不可用（见上）
2. AI 功能（MCP sidecar / AI 问答 / 网页剪藏）需网络，**但核心本地功能
   （笔记/搜索/图谱/导出）完全不受影响** —— 项目定位本地知识库，离线可用性良好

### 遗留风险（同第一轮，仍未解决）

1. webkit2gtk-4.1 无官方麒麟源 → 离线机必须提前备齐该包，是离线部署的头号难点
2. OCR 引擎 aarch64 包未必现成（官方 Release 多为 x64）
3. PDFium 需源码编译（gn/ninja）
4. kysec 可能拦截 .deb 内 sidecar（kb-mcp）启动，需 IT 放行
5. fonts-noto-cjk / libayatana-appindicator3-1 包名在部分麒麟版本不同

## 第五轮：设备码登录失败 → 定位为网络端点问题，改用 PAT 方案

### 失败过程

1. winget 装 gh 静默卡 7 分钟无响应 → 改下便携版，1 分钟完成
   - 位置 `C:/gh-portable/bin/gh.exe`（gh 2.62.0），需 export PATH
2. 设备码登录：第一次进程被超时中断（码 D088-0FCB 作废）
3. 第二次后台常驻生成码 B7D6-5EF1，用户网页授权 → 结果：
   `failed to authenticate via web browser: Post "https://github.com/login/oauth/access_token": unexpected EOF`

### 根因（实测确认，非用户操作问题）

| 端点 | 实测结果 |
|---|---|
| `api.github.com` | ✔ 200，0.6s |
| `github.com/login/oauth/access_token` | ✘ **连续 3 次全部超时（10-15s 无响应）** |

设备码流程最后一步必须访问该超时端点交换 token，浏览器点 Authorize 后
CLI 收不到响应 → 页面置灰/卡住。**这是网络对该端点的限制，与用户操作无关。**

### 处置

放弃设备码流程，改用 **Personal Access Token（PAT）**：
PAT 网页生成后直接使用，完全绕开 oauth/access_token 端点。

已产出 `docs/生成Token指引.md`：3 步生成 PAT + 最小权限说明
（仅 Contents: Read and write）+ 安全提醒（用完吊销）。

### 经验

- 设备码登录在受限网络下不可靠，遇 `unexpected EOF` 应直接换 PAT，不要反复重试
- 排查手法：分别 curl 目标端点，区分「整体不通」与「特定端点不通」
- winget 装大包易卡死，直接下便携版压缩包更快

### 🔴 CI 真正根因（actionlint 1.7.7 定位，前面三轮猜测全未命中）

```
context "matrix" is not allowed here.
available contexts are "github", "inputs", "needs", "vars"
```

**`matrix` 上下文只在 step 级可用；job 级只有 github/inputs/needs/vars。**
把 `matrix.platform` 写进 **job 级 `if:`** 会让**整个工作流解析失败** → 所有 job 都不创建。

症状极具迷惑性：
- run 秒failure，页面提示 "This run likely failed because of a workflow file issue"
- `prepare-release` 是绿的，`release` 完全空白
- `gh run rerun` 报"its workflow file may be broken"
- 远端 YAML 取回本地解析完全正常（11047 字节、无 CRLF、可解析）
- **极易误判为构建失败或 JSON 问题**

### 走过的三条弯路（已写入代码注释，勿改回）

1. 字符串拼 JSON → `[..,..],{..}` 非法 JSON（数组提前闭合+ 尾部孤立对象）
2. 改 bash 数组 + jq → JSON 已合法（CI 日志确认 5 项齐全），症状**依旧**
3. 静态矩阵 + job 级 if逐条判断 → **触发真正根因**

### 最终方案

- 矩阵**静态声明 5 项**，不用 fromJSON、不依赖任何 vars
- 取消按平台跳过能力：公开仓库 Actions 与 arm64 runner 免费无限量，无省额必要
- prepare-release 只做 draft release + tag 归一化

### 🔧 关键工具经验（下次优先用）

**actionlint** 是唯一能提前发现此类问题的工具：
- 通过 `gh api repos/rhysd/actionlint/releases/assets/<id> -H "Accept: application/octet-stream"`
  下载（直连 GitHub releases 会被代理挡，必须走 API）
- pyyaml 只能验语法，**验不出上下文可用性**，这是本次绕三圈的直接原因
- 教训：改 GitHub Actions 前先跑 actionlint，比反复触发 CI 快几个数量级

### 🔴 硬性技术闭环（装包无解的数学证明）

Ubuntu 全部版本的 `libwebkit2gtk-4.1-0` 依赖均为 `libc6 (>= 2.35)`，而本机 glibc 2.31。

```
麒麟基线 = Ubuntu 20.04  →  源里只有 webkit 4.0
Tauri 2   = 必须 webkit 4.1
webkit 4.1 = 只存在于 Ubuntu 22.04(jammy)+  →  要求 glibc 2.35
本机 glibc = 2.31        →  装不了 jammy 的包
```

**无法用 --force-depends 安全绕过**（webkit2gtk 调用大量 2.32+ 符号，强装会启动即崩）。

**同类案例佐证**：Clash Verge Rev（同样是 Tauri 2 应用）在 Mint 20.3（glibc 2.31）上
遇到完全相同问题，结论同样是「装不上，只能源码编译或退 Tauri 1.x」。

> ⚠️ 这修正了我第九轮的错误建议（从 Ubuntu 22.04 ports 抓包）——
> 那对 glibc 2.31 的机器必然失败。

### 三条路径（已产出 dist-kylin/最终结论.md）

**A. 升级麒麟系统（推荐）** —— SP3 glibc 基线更新，自带 4.1 概率高。
额外价值：glibc 2.31（2023-09 构建）已相当旧，未来撞生态天花板会更多，升级是综合收益。
给 IT 的话术：「需 V10 SP3 或更新，部署的 Tauri 2 应用硬依赖 webkit2gtk-4.1，
当前 V10 GFB 的 glibc 2.31 无法满足」。

**B. 源码编译 webkit2gtk-4.1** —— 成本极高（数十GB磁盘、数小时、libicu70 与麒麟自带 ICU 冲突），
不推荐。

**C. 改用 Tauri 1.x** —— 依赖 webkit2gtk-4.0，本机正好有 4.0，**确定可行**。
代价是 1.x/2.x Rust API 差异大、部分插件版本不同。系统无法升级时的唯一可靠选择。

### 重要定性

**这不是项目的问题，是所有 Tauri 2 应用在老版国产系统上的共同生态代差。**
项目侧已全部就绪：aarch64 安装包已产出、云端 ARM 流水线全自动、
